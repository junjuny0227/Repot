# Repot 계획 11: Repot 파일(`repot.json`) 저장과 열기

**Goal:** 내보내기 폴더에 Repot이 다시 읽을 수 있는 파일 `repot.json`을 함께 쓴다. 시작 화면에서 이 파일을 열면 스캔 없이 검토 화면으로 가고, 목적지를 바꿔 다시 내보낼 수 있다. 옛 기기가 없어도 그때 고른 항목을 다시 다룰 수 있게 하고, 다음 단계(기기 비교, 앱으로 복원, CLI)가 읽을 공통 형식을 만든다.

**Architecture:** `repot-core`에 `snapshot` 모듈을 더한다. 파일 형식은 내부 모델(`Item`)을 그대로 직렬화하지 않고, 버전이 붙은 별도 타입(`snapshot::v1`)으로 정의한 뒤 내부 모델과 서로 변환한다. `build_export`의 첫 인자는 `Env` 대신 `ConfigSource`이고, 설정 파일 내용을 그것으로 읽는다. 실제 기기에서는 `Env`가, 열린 파일에서는 파일에 담긴 내용이 `ConfigSource`다. 데스크톱 앱은 "현재 세션"을 스캔 결과 또는 열린 파일로 두고, 출발 OS도 세션에서 가져온다.

**Tech Stack:** Rust(serde, serde_json), React, TypeScript, Vitest

**Spec:** `docs/specs/2026-11-02-repot-mvp-design.md` §2·4·5·10·11·12·13·15·16

## Global Constraints

- **새 의존성 없음.** `serde_json`은 이미 core 의존성이다. 파일 고르기는 이미 있는 `dialog:allow-open` 권한으로 한다. `Cargo.lock`, `pnpm-lock.yaml`, Tauri capability는 바뀌지 않아야 한다.
- **기기를 바꾸지 않는다.** `repot.json`은 내보내기 폴더 안에만 쓴다. 열기는 사용자가 고른 파일 하나를 읽기만 한다. 읽기는 `Env::read_file`을 거친다.
- **고른 것만 담는다.** `repot.json`에는 이번 내보내기에 실제로 들어간 항목만 넣는다. 사용자가 빼거나, 목적지에서 쓸 수 없거나, 경고로 빠진 항목은 넣지 않는다.
- **비밀정보는 내보내기와 똑같이 가린다.** 설정 파일 내용은 사용자가 보이기로 한 줄 말고는 `<REDACTED>`로 가린 상태로 담는다. 파일을 연 뒤에는 가린 줄을 되살릴 수 없다.
- **열린 파일은 신뢰하지 않는다.** 크기 상한(5 MB), 형식 표지, 버전, 경로(상대 경로만, `..`·절대 경로·드라이브 문자 금지, 설정 파일·셸 플러그인은 그 항목의 Provider가 스캔하는 자리만, 스펙 §10), URL(`https://`만), 값 허용 패턴을 확인한다. 형식이 틀린 항목은 버리고 개수만 알린다.
- **core는 문장을 만들지 않는다.** 열기 오류는 종류(enum)로만 돌려주고, 문구는 UI 로캘(en·ko·ja·zh-Hans)에 둔다. `repot.json` 안의 키와 값은 영어 식별자다.
- **같은 결과.** 같은 항목과 목적지라면, 기기에서 바로 내보낸 결과와 `repot.json`을 열어 다시 내보낸 결과가 같아야 한다(생성 시각 줄 제외). 이것을 core 테스트로 고정한다.
- **직렬화 변경:** `ScanResult`·`Item` 모양은 바꾸지 않는다. 바꿀 일이 생기면 `scan.json` fixture를 다시 생성한다.
- AGENTS.md는 하위 작업자가 고치지 않는다. 필요한 줄은 부모가 고친다.

## 결정과 이유

**왜 내부 모델과 분리된 타입인가.** `Item`은 앱 안에서 계속 바뀐다(계획 9에서 `Portability`가 바뀐 것처럼). `Item`을 그대로 파일에 쓰면, 내부 필드 이름 하나만 바꿔도 사용자가 가진 옛 파일을 못 읽게 된다. 파일 형식은 한 번 공개하면 이후 모든 버전이 읽어야 하는 약속이므로, `snapshot::v1` 타입을 따로 두고 변환 함수 두 개(`Item → v1`, `v1 → Item`)만 내부 모델을 안다. 변환이 조금 중복되지만, 형식이 바뀌는 지점이 한 곳으로 모인다. 구조 타입(`ItemV1`, `DetailsV1`, `TargetPathV1`)은 따로 두고, 값 enum(`Category`, `PackageManager`, `Portability`, `Finding` 등)은 모델 것을 그대로 쓴다. 이 enum의 철자는 커밋한 v1 fixture 테스트가 고정하므로, 바꾸면 테스트가 깨진다. 바꿔야 할 때는 그 enum의 v1 사본을 먼저 만든다.

**버전 규칙.**
- 파일은 `"format": "repot"`, `"schemaVersion": 1`로 시작한다.
- 같은 `schemaVersion` 안에서는 더하기만 한다. 선택 필드를 더하거나 enum 값을 더할 수 있다. 읽는 쪽은 모르는 필드를 무시하고, 모르는 enum 값이 든 항목은 그 항목만 버리고 개수를 알린다.
- 필드를 지우거나 이름·뜻을 바꾸면 `schemaVersion`을 올리고, 읽는 쪽에 옛 버전을 새 타입으로 바꾸는 함수를 둔다. 옛 버전 읽기는 지우지 않는다.
- 앱보다 새 `schemaVersion`이면 읽지 않고 "새 Repot이 필요" 오류를 낸다.
- `tests/fixtures/snapshot/v1-*.json`은 한 번 커밋하면 고치지 않는다. 앞으로의 모든 버전이 이 파일을 읽을 수 있어야 한다는 테스트다.

**왜 설정 파일 내용을 JSON 안에 넣는가.** `files/` 아래 파일은 목적지 OS에 맞춰 이미 바뀐 상태다(예: Windows 목적지면 `credential.helper` 줄이 주석 처리됨). 이것을 다시 다른 OS로 내보내면 변환이 겹친다. 그래서 `repot.json`에는 출발 기기 형태 그대로, 비밀정보만 가린 내용을 넣는다. 설정 파일은 대부분 수 KB라 파일 하나에 담아도 크지 않고, 파일 하나만 옮기면 되는 편이 다루기 쉽다. `files/`와 내용이 겹치지만 용도가 다르다.

**왜 내보낼 때마다 쓰는가(따로 저장 버튼 없음).** 저장 버튼을 따로 두면 "어느 것을 저장했나"가 내보내기와 어긋날 수 있다. 내보내기 폴더가 곧 "이 기기에서 옮기기로 한 것"이고, `repot.json`은 그 폴더를 기계가 읽는 형태로 적은 것이다. 형식(스크립트/매니페스트)과 상관없이 항상 쓴다.

**왜 고른 항목만인가.** 전체 스캔 결과를 담으면 사용자가 일부러 뺀 설정 파일까지 파일에 남는다. "고른 것만 기기를 떠난다"는 원칙을 지키는 쪽을 택했다. 대가로, 목적지 때문에 빠진 항목(예: Windows 목적지로 내보낼 때의 macOS 전용 앱)은 나중에 다른 목적지로 다시 내보낼 수 없다. §15에 적는다.

**이번에 하지 않는 것.** 현재 기기와 비교(이미 있는 것/빠진 것), 앱 안에서 복원, CLI는 이 형식을 쓰는 다음 계획으로 미룬다. 형식을 먼저 공개하고 실제로 써 본 뒤 넓힌다.

## 파일 형식 (v1)

```json
{
  "format": "repot",
  "schemaVersion": 1,
  "createdAt": "2026-11-04T10:00:00Z",
  "repotVersion": "0.5.0",
  "source": { "os": "macOs" },
  "items": [
    {
      "id": "brew:formula:ripgrep",
      "provider": "brew",
      "category": "packageManager",
      "name": "ripgrep",
      "version": "14.1.1",
      "description": "Search tool like grep and The Silver Searcher",
      "catalogId": null,
      "details": { "package": { "manager": "brew", "kind": "formula" } }
    },
    {
      "id": "git:file:.gitconfig",
      "provider": "git",
      "category": "git",
      "name": ".gitconfig",
      "details": {
        "configFile": {
          "source": "/Users/me/.gitconfig",
          "target": { "home": ".gitconfig" },
          "content": "[user]\n\tname = Me\n[github]\n\ttoken = <REDACTED>\n",
          "maskedLines": [{ "line": 4, "name": null }],
          "revealedLines": []
        }
      }
    }
  ]
}
```

- `id`, `provider`, `category`, `details`의 값과 이름은 지금 `Item` 직렬화와 같은 camelCase를 쓴다. 같아 보여도 별도 타입이므로, 내부가 바뀌면 변환 함수만 고친다.
- 항목에는 `origin`, `portability`, `findings`도 담는다(예시에서는 줄임). `portability`는 Provider 코드만 정할 수 있어 열 때 다시 계산할 수 없고, `findings`는 검토 화면이 비밀정보·OS 전용 줄을 보여주는 데 쓴다. `findings` 중 `Duplicate`는 열 때 다시 계산하고, `Unreadable` 항목은 내보내지 않으므로 담지 않는다.
- `maskedLines`는 가린 줄과 비밀 이름이다. `ghp_…`처럼 이름 없는 토큰은 `<REDACTED>`로 바뀐 뒤에는 다시 감지되지 않으므로, 다시 내보낼 때 이 기록을 합친다. `revealedLines`는 처음 내보낼 때 보이기로 한 줄이고, 열린 파일에서 다시 내보낼 때 그대로 쓴다.
- `createdAt`은 UTC ISO 8601(분 단위, `2026-11-04T10:00Z`), `source.os`는 `Os` 직렬화와 같다(Linux는 계열 포함).

## 모델 변경 (core)

```rust
// crates/core/src/snapshot/mod.rs
pub struct Snapshot { pub created_at: String, pub repot_version: String, pub source: Os, pub items: Vec<Item>, pub configs: BTreeMap<String, StoredConfig> /* item id → 내용 */ }
pub struct StoredConfig { pub content: String, pub masked: Vec<(u32, Option<String>)>, pub revealed: Vec<u32> }
pub struct OpenedSnapshot { pub snapshot: Snapshot, pub skipped_items: usize }
pub enum SnapshotError { TooLarge, NotRepotFile, NewerVersion { found: u32 }, Invalid }
pub fn parse_snapshot(text: &str) -> Result<OpenedSnapshot, SnapshotError>;
pub fn render_snapshot(created_at: &str, repot_version: &str, source: Os, items: &[(Item, Option<StoredConfig>)]) -> String;

// crates/core/src/export
pub struct ConfigText { pub text: String, pub masked: Vec<(u32, Option<String>)>, pub revealed: Option<Vec<u32>> }
pub trait ConfigSource { fn read_config(&self, item: &Item) -> Option<ConfigText>; }
impl<E: Env + ?Sized> ConfigSource for E   // ItemDetails::ConfigFile.source 경로를 읽는다
impl ConfigSource for Snapshot             // configs[item.id]
pub fn build_export(configs: &(impl ConfigSource + ?Sized), req: &ExportRequest<'_>) -> ExportBundle;
```

- `Env`에 대한 일괄 구현이 있어서 기존 호출(`build_export(&env, …)`, `build_export(self.env.as_ref(), …)`)은 그대로 컴파일된다.

- `build_export`는 항목을 고르고 검증하는 기존 흐름을 그대로 쓰고, 실제로 들어간 항목으로 `repot.json`을 만들어 스크립트·매니페스트 다음, `files/` 앞에 넣는다.
- 열린 파일의 설정 내용은 이미 가려져 있으므로 요청의 `reveal_secret_lines` 대신 파일의 `revealedLines`를 쓰고, 파일의 `maskedLines`를 다시 감지한 결과와 합친다.
- `ExportMeta`에 필드를 더하지 않고, `created_at()`이 `date`와 `generated_at`에서 ISO 시각을 만든다.

## Tauri 명령 변경

| 명령 | 변경 |
|---|---|
| `open_snapshot` (새로 추가) | 경로를 받아 `Env::read_file`로 읽고 파싱한다. 성공하면 세션을 이 파일로 바꾸고 `{ scan: ScanResult, source: Os, createdAt, repotVersion, skippedItems }`를 돌려준다. 실패하면 오류 종류 문자열(`tooLarge`·`notRepotFile`·`newerVersion:<n>`·`invalid`·`readFailed`)을 돌려준다. |
| `scan` | 세션을 새 스캔 결과로 바꾼다. 출발 OS는 `detect_os` 값이다. |
| `availability_for`, `preview_export`, `export` | 세션의 출발 OS와 `ConfigSource`를 쓴다. |

`AppState`의 `scan`과 `source`를 `session: Mutex<Option<Session>>` 하나로 합친다. `Session { source: Os, scan: ScanResult, configs: Live | Snapshot(Snapshot) }`. 이렇게 하면 "스캔 결과는 A 기기, 출발 OS는 B" 같은 어긋난 상태를 만들 수 없다.

## UI 변경

- 시작 화면: 스캔 버튼 왼쪽에 보조 버튼 "Repot 파일 열기…". 파일 대화상자는 `*.json` 필터를 쓴다.
- 검토 화면: 열린 파일이면 사이드바 아래(스캔의 "감지 안 됨/실패" 목록 자리)에 "macOS에서 2026. 11. 4.에 만든 Repot 파일"을 보여준다. 버린 항목이 있으면 "이 버전의 Repot이 읽을 수 없는 항목 n개를 건너뛰었습니다"를 덧붙인다. 툴바에 두면 목적지 선택이 좁아져 라벨이 깨진다(렌더링으로 확인). 비밀정보 줄은 "보이기" 토글을 숨기고, 발견 문구도 "Repot 파일에 가린 채 저장된 비밀 정보입니다. 복원한 뒤 값을 채우세요"로 바꾼다.
- 세션 출발 OS는 `state.opened?.source ?? state.source`(`sessionSource`)다. `state.source`는 계속 이 기기의 OS이고, 새로 스캔하거나 처음으로 돌아가면 `opened`가 지워진다.
- 열기 실패는 기존 오류 표시 방식으로, 종류별 문구를 네 로캘에 둔다.
- 내보내기 미리보기 파일 트리에 `repot.json`이 보인다. 완료 화면 안내에 "이 폴더의 `repot.json`을 Repot에서 열면 다시 고를 수 있습니다" 한 줄을 더한다.

## Review Focus

1. `snapshot::v1` 타입이 내부 모델과 분리되어 있고, 변환 함수 밖에서 `Item`을 직렬화해 파일에 쓰는 곳이 없는가.
2. v1 fixture가 커밋되어 있고, 모르는 필드·모르는 enum 값·새 `schemaVersion`·형식 표지 없음·5 MB 초과·`..` 경로·`http://` URL에 대한 테스트가 있는가.
3. 바로 내보내기와 파일을 거친 내보내기의 결과가 같은가(목적지 3종 이상).
4. `repot.json`에 고르지 않은 항목이나 가리지 않은 비밀이 들어갈 길이 없는가. 보이기로 한 줄만 원문인가.
5. 세션이 하나로 묶여 출발 OS와 항목이 어긋날 수 없는가. 새로 스캔하면 열린 파일 세션이 사라지는가.
6. 네 로캘에 새 키가 모두 있고, 열린 파일 표시와 비밀정보 안내가 맞는가.
