# Repot 계획 16: SSH 클라이언트 설정 (`~/.ssh/config`)

**Goal:** 새 기기에서 `ssh github-work`, `ssh bastion` 같은 별칭이 그대로 동작하도록 SSH 클라이언트 설정 `~/.ssh/config`(와 그 파일이 `Include`로 불러오는 `~/.ssh` 안의 파일)를 옮긴다. 1단계는 설정만 옮긴다. 개인 키는 옮기지 않고, 설정이 가리키는 키 경로를 내보내기 README와 복원 요약에 적어 사용자가 직접 복사하게 한다.

**Architecture:** 새 Provider `ssh`(새 분류 `Category::Ssh`)가 설정 파일마다 기존 `ItemDetails::ConfigFile { source, target: TargetPath::Home(".ssh/…") }` 항목을 만든다. 새 `Step` 종류는 없다. 복사·백업·비교·`repot.json`은 `.gitconfig`·`.zshrc`와 같은 길(`config_file_item` → `Step::CopyFile` → `copy_file`/`Copy-RepotFile`, `prepare_config`, `compare::same_contents`)을 쓰고, SSH만의 규칙 세 가지만 더한다: OS 전용 줄 주석 처리(`prepare_config`), `.ssh/` 아래 대상의 권한(bash 렌더러), 키 경로 안내(`ExportNote`).

**Tech Stack:** Rust, React, TypeScript, GitHub Actions. 새 의존성 없음.

**Spec:** `docs/specs/2026-11-02-repot-mvp-design.md` §2·6·7·8·9·10·13·15·16

## Global Constraints

- **새 의존성 없음.** `Include`의 와일드카드는 마지막 경로 조각의 `*`·`?`만 직접 맞춘다. glob 크레이트를 더하지 않는다.
- **키는 읽지 않는다.** Provider는 `~/.ssh/config`와 `Include`로 불러온 설정 파일만 `Env::read_file`로 읽는다. `IdentityFile`이 가리키는 파일은 열지도, 있는지 확인하지도 않는다. 경로 문자열만 설정 파일에서 꺼낸다.
- 파일 읽기와 폴더 목록은 모두 `Env`를 거친다. 테스트는 `FakeEnv`(`with_file`, 폴더 목록)로만 한다.
- core는 문장을 만들지 않는다. 화면 문구는 네 로캘(`en`, `ko`, `ja`, `zh-Hans`)에 같은 키로 둔다. 생성 파일(스크립트 출력, README)은 영어다.
- `repot.json`은 v1 그대로 enum 값만 더한다(`Category::Ssh`, `FindingKind::KeyFile`, `FindingKind::ExternalInclude`). 이전 앱은 SSH 항목을 건너뛰고 개수를 알린다.
- 앱은 기기를 바꾸지 않는다. `~/.ssh`에 쓰는 것은 사용자가 실행하는 복원 스크립트뿐이다.
- AGENTS.md는 하위 작업자가 고치지 않는다.

## 결정과 이유

**옮기는 것은 설정 파일뿐.** `~/.ssh/config`는 별칭·사용자 이름·포트·점프 호스트 같은 사람이 쓴 설정이라 옮길 가치가 크고, 비밀이 거의 없다. 개인 키는 원문 그대로 내보내기 폴더에 두면 폴더를 USB나 클라우드로 옮기는 동안 그대로 노출되므로 암호화 없이는 다루지 않는다(아래 "2단계").

**`known_hosts`는 옮기지 않는다.**
- 기기마다 쌓이는 신뢰 기록이다. 새 기기에서 처음 접속할 때 지문을 확인하면 OpenSSH가 다시 만든다. 옮기지 않아도 기능이 줄지 않는다.
- 접속한 적 있는 모든 호스트 이름·IP(사내 서버 포함)가 들어 있다. macOS 기본값은 `HashKnownHosts no`라 평문이다. 내보내기 폴더가 기기 밖으로 다니는 동안 접속 이력이 새는 것은 §3 원칙 3(의심스러우면 보수적으로)에 어긋난다.
- 오래된 키가 남아 있으면 서버 키가 정상적으로 바뀐 경우와 공격을 구별하는 경고를 오히려 흐린다.
- 같은 이유로 `known_hosts.old`, `authorized_keys`(이 기기에 들어올 수 있는 키 목록, 옮기면 접근 권한을 넓힌다), `*.pub`, `environment`, `rc`, `agent/` 등 `~/.ssh`의 나머지는 옮기지 않는다.

**`Include`는 `~/.ssh` 안의 파일만 따라간다.** `Include config.d/*`처럼 사람이 나눠 쓴 설정은 본 파일과 한 몸이라 같이 옮겨야 별칭이 산다. 반면 `~/.ssh` 밖의 Include(이 Mac의 실제 설정에도 있는 `Include ~/.orbstack/ssh/config`, colima·Docker Desktop 등)는 다른 도구가 만들고 관리하는 기기 전용 파일이라 따라가지 않는다. 그 `Include` 줄은 본 파일에 그대로 남기고, 그 줄에 `FindingKind::ExternalInclude { path }`를 붙여 상세 패널에 "이 파일은 다른 도구가 관리해 옮기지 않음"을 줄 번호와 함께 보여준다(사용자 결정, 2026-11-05). 사용자가 할 일은 없으므로 "경고 있는 것만" 필터에는 잡히지 않는다. OpenSSH는 Include가 가리키는 파일이 없으면 오류 없이 넘어간다(이 Mac의 OpenSSH 10.5에서 `ssh -G`로 확인, Linux·Windows는 Task 3의 CI에서 확인). 규칙:
- 인자는 공백으로 나뉜 여러 개일 수 있고, `Host`/`Match` 블록 안에 있어도 따라간다(블록 조건은 복원 후에도 같은 줄에 남는다).
- `~/`로 시작하면 홈 기준, 상대 경로는 `~/.ssh` 기준(OpenSSH 규칙), 절대 경로는 홈의 `.ssh/` 아래일 때만. 정규화한 경로에 `..`가 있거나 `.ssh` 밖이면 따라가지 않는다.
- 와일드카드는 마지막 조각에만 허용한다(`config.d/*`, `conf.d/*.conf`). 폴더를 `Env::list_dir`로 읽어 이름순으로 맞춘다(OpenSSH의 glob 순서). 중간 조각에 와일드카드가 있으면 따라가지 않는다.
- 깊이 16(OpenSSH `READCONF_MAX_DEPTH`), 파일 32개까지. 한 파일은 한 번만 항목이 된다(순환 방지).
- 따라간 파일도 이름이 금지 목록(`known_hosts*`, `authorized_keys*`, `*.pub`, `id_*`, `environment`, `rc`)에 있거나 내용에 `-----BEGIN … PRIVATE KEY-----`가 있으면 항목을 만들지 않는다. `Include *`처럼 넓은 패턴이 키를 끌어오는 것을 막는다.
- 이 금지 규칙은 `ssh::is_config_target(rel)` 하나로 두고, 스캔과 `repot.json` 열기(아래)가 같이 쓴다.

**OS 간 경로.** 대상은 `TargetPath::Home(".ssh/config")`로 기존 렌더러가 그대로 해석한다. bash `"$HOME/"'.ssh/config'`, PowerShell `(Join-Path $HOME '.ssh\config')`이고, Windows PowerShell의 `$HOME`은 `%USERPROFILE%`이라 Windows OpenSSH가 읽는 `%USERPROFILE%\.ssh\config`와 같다. 내용의 `IdentityFile ~/.ssh/id_ed25519`처럼 `~`로 시작하는 경로와 `%d`(홈) 같은 토큰은 세 OS의 OpenSSH가 모두 해석하므로 바꾸지 않는다. 바꾸는 것은 아래 OS 전용 줄뿐이다.

**OS 전용 줄은 주석 처리한다(`IgnoreUnknown`을 앞에 넣지 않는다).** OpenSSH는 모르는 옵션을 만나면 `Bad configuration option: usekeychain` / `terminating, 1 bad configuration options`로 설정 전체를 거부한다(이 Mac에서 모르는 옵션으로 `ssh -G` 종료 코드 255 확인, upstream을 따르는 Linux·Windows OpenSSH도 같다고 보고 CI에서 확인). 그래서 macOS 전용 `UseKeychain`이 든 파일을 그대로 Linux·Windows로 옮기면 그 기기의 `ssh`가 모든 호스트에서 실패한다. 세 가지 방법 중:
- 경고만: 복원 직후 `ssh`가 깨지므로 안 된다.
- 맨 앞에 `IgnoreUnknown UseKeychain` 넣기: 줄 번호가 하나씩 밀려 가린 비밀 줄 목록·Finding·비교가 모두 어긋나고, 사용자가 쓰지 않은 줄을 앱이 만든다. `IgnoreUnknown`은 그 줄보다 앞에서 선언해야 하므로 Include된 파일까지 생각하면 위치도 애매하다.
- **주석 처리(채택):** Git의 `credential.helper`와 같은 길(`# [repot] … # <key> is OS-specific; adjust it for <OS>`)이다. 줄 번호가 그대로고, 사용자가 무엇이 바뀌었는지 파일과 요약에서 본다. 출발 파일에 이미 `IgnoreUnknown UseKeychain`이 있어도 주석 처리한다. 그 줄은 Linux·Windows에서 할 일이 없으니 잃는 것이 없고, 규칙이 단순해진다.

주석 처리하는 줄(출발과 목적지 OS 종류가 다를 때만, `prepare_config`가 내보내기와 비교에서 같이 쓴다):

| 키워드 | 조건 | 이유 |
|---|---|---|
| `UseKeychain` | 목적지가 macOS가 아님 | Apple OpenSSH 전용 옵션, 다른 OS는 설정 전체를 거부 |
| `ControlMaster`, `ControlPath`, `ControlPersist` | 목적지가 Windows | Windows OpenSSH는 연결 다중화를 지원하지 않는다(Win32-OpenSSH Project Scope, issue #405·#1328). 이 옵션을 쓰면 접속이 실패한다고 보고되어 있다(CI에서 확인) |
| `IdentityFile`, `CertificateFile`, `IdentityAgent`, `UserKnownHostsFile`, `ControlPath` | 값이 절대 경로(`/…`, `C:\…`, `\\…`)이거나 `~/Library/`로 시작 | 출발 OS의 경로라 목적지에 없다. 예: 1Password `IdentityAgent "~/Library/Group Containers/…/agent.sock"`은 `~`로 시작하지만 macOS 전용 위치다 |

- 키워드는 대소문자를 무시해 찾고, Finding의 `key`에는 위 표의 표기를 쓴다. 줄 형식은 `키워드 값`과 `키워드=값` 둘 다, 값의 큰따옴표를 벗긴다.
- 스캔 Finding(`OsSpecificLine`)은 목적지를 모르므로 `UseKeychain`과 경로 줄에만 붙인다(UI의 기존 문구 "다른 OS에서는 주석 처리됨"이 맞는 경우). `Control*`는 Windows로 내보낼 때만 주석 처리되고 README·요약의 `Notes`에 남는다.
- `ProxyCommand`, `Match exec` 속 명령(`nc`, `/usr/bin/…`)은 판단하지 않는다(§15).

**권한.** OpenSSH 클라이언트는 `~/.ssh/config`가 그룹·다른 사용자에게 쓰기 가능하면 `Bad owner or permissions`로 거부한다. 기존 `copy_file`은 새 파일을 umask(보통 0644)로 만들고, 덮어쓸 때는 기존 파일 권한을 유지한다. 그래서 bash 렌더러는 대상이 `.ssh/` 아래(`TargetPath::is_private()`: `Home(rel)`의 첫 조각이 `.ssh`)일 때 `copy_private_file`을 쓴다. umask 077 하위 셸에서 `copy_file`을 불러 새로 만드는 폴더(`~/.ssh`, `~/.ssh/config.d`)는 0700, 새 파일은 0600이 되고, 복사가 끝나면 `chmod 600`을 한 번 더 해 기존 파일도 0600으로 맞춘다. 이미 있던 `~/.ssh` 폴더의 권한은 바꾸지 않는다(사용자가 정한 것이고 클라이언트 설정에는 필요 없다). 백업은 기존 `cp -p`라 원래 권한을 유지한다. Windows는 ACL을 건드리지 않는다. `Copy-Item`이 만든 파일은 `%USERPROFILE%`의 상속 ACL(사용자, SYSTEM, Administrators)을 받고, 이것이 Windows OpenSSH가 요구하는 조건이다. CI가 Windows 기본 경로로 `ssh -G`를 돌려 권한 검사까지 확인한다(Task 3).

**백업과 "이미 됨".** 기존 설정 파일과 같다. 같은 내용이면 `Already done`, 다르면 `<파일>.repot-backup-<YYYYMMDDHHMMSS>`로 백업한 뒤 덮어쓴다. 처음 선택도 다른 설정 파일처럼 목적지에서 쓸 수 있으면 켜진 채로 시작한다. 비교 후 "내용 다름"은 계획 12대로 꺼진 채 시작한다.

**키 안내.** 설정의 `IdentityFile`·`CertificateFile` 값(주석 처리된 줄 포함)을 경로 문자열 그대로 모아 안내한다.
- 스캔: 그 줄에 `FindingKind::KeyFile { path }`를 붙인다. 상세 패널이 "Repot은 키를 옮기지 않음, 직접 복사"를 줄 번호와 함께 보여준다. 사용자가 할 일이 있는 표시라 "경고 있는 것만" 필터에도 잡힌다.
- 내보내기: `prepare_config`가 `ExportNote::SshKey { file, line, path }`를 만든다. 렌더러는 이 노트를 일반 `Notes`와 나눠 `Copy these SSH keys yourself` 제목 아래에 경로마다 한 번씩(처음 나온 줄 기준) 적는다. 복원 요약(bash·PowerShell), 매니페스트 README, 통합 스크립트 형식의 README(지금은 대응 패키지가 있을 때만 쓰는데, 키 노트가 있어도 쓴다)에 같은 목록이 들어간다.
- SSH 설정을 내보내면 키 줄이 없어도 한 줄 안내를 남긴다: Repot은 키를 옮기지 않으니 쓰는 키(기본 이름 `id_ed25519`, `id_ecdsa`, `id_rsa`)와 `.pub`을 직접 복사하라는 것. `IdentityFile`이 없는 설정도 OpenSSH는 기본 키 이름을 쓰기 때문이다.

**비밀정보.** §8을 그대로 쓴다(토큰 형식, 자격 증명 URL, 개인 키 블록). 하나만 더한다. 이름 기반 규칙의 줄 앞머리에 `SetEnv`(대소문자 무시)를 허용해 `SetEnv DEPLOY_TOKEN=abc123`의 값을 가린다. `SetEnv`는 한 줄에 `NAME=value`를 여럿 쓸 수 있지만 첫 이름이 맞으면 줄 끝까지를 값으로 보고 가린다(덜 가리는 것보다 더 가리는 쪽). `ProxyCommand cloudflared … --service-token-secret abc` 같은 명령 인자는 알려진 토큰 형식일 때만 잡힌다(§15). 이름 기반 규칙을 명령 인자까지 넓히지 않는다. `--token`·`-i` 같은 정상 인자까지 가려 복원된 설정이 동작하지 않을 위험이 더 크다고 판단했다(사용자 결정, 2026-11-05).

**`repot.json`.** 항목은 기존 `DetailsV1::ConfigFile`(내용은 출발 기기 형태, 비밀만 가림) 그대로다. v1에 더하는 것은 `category: "ssh"`와 finding `{"keyFile": {"path": "…"}}`, `{"externalInclude": {"path": "…"}}` enum 값뿐이다. 열 때 안전 검사를 하나 더한다. 지금은 `ConfigFile`의 `home` 대상이 상대 경로이고 `..`가 없기만 하면 받으므로, 남이 준 `repot.json`이 `git` 항목으로 `.ssh/authorized_keys`를 쓰게 만들 수 있다. 그래서 대상의 첫 조각이 `.ssh`(대소문자 무시, macOS 파일 시스템이 대소문자를 구별하지 않는다)이면 `provider == "ssh"`이고 `ssh::is_config_target(rel)`을 통과해야 하고, 반대로 `provider == "ssh"`면 대상이 `.ssh/` 아래여야 한다. 어긋나면 그 항목을 건너뛰고 개수를 알린다. 이 검사는 #108이 만든 `snapshot::is_scanned_config_target`에 `ssh` provider와 `ssh::is_config_target`을 더하는 것으로 구현한다.

**사용 가능 여부.** `Portability::Any`. 세 OS 모두 OpenSSH 클라이언트가 기본으로 있고(Windows 10 1809 이상), 차이는 위 주석 처리가 맡는다. `ssh`가 없는지 확인하는 사전 점검은 넣지 않는다. 파일 복사에는 도구가 필요 없기 때문이다.

**CLI와 앱.** CLI `scan`은 분류 목록에 `SSH`를 더하고(`text.rs`, `run.rs`의 분류 순서), 나머지는 core를 그대로 쓴다. 앱은 사이드바 분류 `SSH`, 카탈로그 설명 하나, Finding 문구 하나를 네 로캘에 더한다.

## 예시

`~/.ssh/config` (macOS):

```
 1  Include config.d/*
 2  Include ~/.orbstack/ssh/config
 3
 4  Host *
 5    AddKeysToAgent yes
 6    UseKeychain yes
 7    IdentityFile ~/.ssh/id_ed25519
 8
 9  Host github-work
10    HostName github.com
11    User git
12    IdentityFile ~/.ssh/work_ed25519
13    IdentitiesOnly yes
14
15  Host bastion
16    HostName bastion.example.com
17    ControlMaster auto
18    ControlPath ~/.ssh/cm-%r@%h:%p
19    ControlPersist 10m
20    SetEnv DEPLOY_TOKEN=abc123
```

`~/.ssh/config.d/work`:

```
Host *.corp.example.com
  User alice
  ProxyJump bastion
```

스캔 결과(`scan.json` 모양). 1행은 `config.d/work` 항목을 하나 더 만들고, 2행은 `~/.ssh` 밖이라 따라가지 않는다.

## Review Focus

1. Provider가 `IdentityFile` 대상 파일을 읽거나 확인하지 않는가(`FakeEnv`에 키 파일을 두지 않아도 테스트가 같고, 읽기 호출 기록에 없는가).
2. `Include` 규칙: `~/.ssh` 밖·`..`·중간 와일드카드는 따라가지 않고, 금지 이름과 개인 키 블록이 든 파일은 항목이 되지 않으며, 순환·깊이·개수 제한이 걸리는가.
3. 주석 처리가 목적지별 표와 정확히 같은가(Linux는 `UseKeychain`만, Windows는 `Control*`까지, 같은 OS는 없음). 줄 번호가 바뀌지 않아 가린 줄 목록과 맞는가. 비교(계획 12)가 같은 `prepare_config`를 거치는가.
4. bash `copy_private_file`이 새 폴더 0700·파일 0600, 기존 파일도 0600으로 만들고, 기존 `~/.ssh` 권한은 그대로 두는가. 백업·`Already done`이 기존 설정 파일과 같은가. bash 3.2·shellcheck·PSScriptAnalyzer.
5. 키 목록이 경로마다 한 번, 요약·README 둘 다에 있고, 키 내용이나 존재 여부를 말하지 않는가.
6. `repot.json`: 고정 v1 fixture 유지, SSH 항목 왕복, `git` 항목으로 `.ssh/authorized_keys`를 쓰려는 파일과 `ssh` 항목으로 `.ssh` 밖을 쓰려는 파일을 건너뛰는가.
7. 네 로캘의 같은 키, `catalog.test.ts`, 재생성한 `scan.json`.
